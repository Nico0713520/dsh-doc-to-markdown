## Cat Wu:AI 时代,产品经理的工作方式已被彻底重构 

学习来源:Cat Wu(Anthropic Claude Code 产品负责人)官方博客分享,Datawhale 翻译 整理 原文:Claude Code 的产品经理,把她用 AI 重构工作流的方式全说了 学习时间:2026-06-26 

### 一、这个人是谁,为什么值得听 

Cat Wu,现任 Anthropic 旗下 Claude Code 和 Cowork 的产品负责人。她的职业轨迹: 工程师 → VC(⻛险投资)→ Anthropic 研究 PM 

这不是三个不相关的岗位,是同一套底层能力在不同场景的三次应用: 

- 工程师阶段练出了自动化本能:遇到重复劳动就写代码解决。即使后来在 VC,她也闲不住 写脚本自动扫 Twitter 找新公司和监测 GitHub 热⻔项目。 

- VC 阶段训练了在信息不完整时做判断的能力。VC 永远没法掌握全部信息,必须快速评估一 个项目值不值得投。这种"在不确定中做决策"的习惯,直接延续到她后来做 PM 的"快速试 错"逻辑。 

- 研究 PM 把前两者合在一起:用工程师的动手能力自己做原型,用 VC 的判断力在快速变化 的模型能力中抓机会。 

2024 年秋天 Claude Code 内测期间,她做了几百小时的工作"Streamlit 应用分析用戶反 馈、跑评估测试测模型边界、搭强化学习环境"一行代码没手写,全是跟 Claude Code 对话 完成的。PM 有想法不用等工程师排期,自己下午就能出原型。这个经历直接塑造了她后来的 整套工作方法论。 

### 二、三个工具的分工架构:按职责层级划分 

Cat Wu 日常使用三个工具,不是按"任务类型"分,而是按职责层级和权限范围分: 

|工具|职责层级|权限范围|干什么|
|---|---|---|---|
|Claude.ai|大脑层(思维)|最小:纯对话|想策略、讨论棘手问题、推理拆解<br>"只负责想,不执行|
|Claude Code|执行层(动手)|中等:代码域|写原型、跑脚本、跑数据"输出<br>是代码的都扔这里|
|Cowork|管家层(系统操<br>作)|最大:跨应用跨系<br>统|清邮件、管待办、做PPT、翻<br>Slack查决策历史、订机票酒店|



##### 三层从内到外:思维 → 执行 → 系统级操作,权限逐层放大。 

判断标准不是"这是什么任务",而是 **"我要什么输出"**。输出是思路就用 Claude.ai,输出是 代码就用 Claude Code,输出是系统操作就用 Cowork。 

#### 生态产品解析 

文章涉及的三个 Anthropic 产品: 

- AskUserQuestion:Claude Code 内置工具。AI 执行过程中遇到不确定的事,主动弹出问 题问用戶,而不是自己猜然后跑偏。本质是把人类嵌入 AI 的执行循环"卡住就停,不硬 跑。 

- Todo Lists:Claude Code 的待办列表。AI 执行复杂任务时自动建清单,做完一项勾一 项。关键转折:老模型经常忘勾,团队加了个自动提醒补丁;Opus 4.6 出来后模型自己就 知道勾了,补丁直接删掉。 

- • Cowork:Anthropic 的桌面级 AI 代理,能打开应用、翻浏览器、填表格、读邮件。相当 于 Anthropic 官方版的"OpenClaw""都是让 AI ⻓出"手"来操控桌面。区别在于 Cowork 是封闭生态,和 Claude 深度绑定;OpenClaw 是开源第三方方案。Anthropic 曾 封禁 OpenClaw,说明桌面代理这个入口他们看得很重。 

### 三、四个工作方式转变 

#### 转变 1:从⻓期路线图到短周期实验 

传统做法:花两周调研 → 写 PRD → 开评审会 → 排进路线图 → 等工程师。整个流程两三个 月。 

现在做法:鼓励所有人随时做"Side Quest"。有想法?别开会了,下午自己试。测测你觉得"AI 应该做不到"的功能,或者故意给模型出难题看它能到哪一步。 

Anthropic 最火的几个功能(桌面版 Claude Code、AskUserQuestion、Todo Lists)都是这 么玩出来的,不是规划出来的。 

底层原因:模型能力每 16 个月提升 41 倍,你做规划时的技术限制,两个月后可能就消失了。 ⻓期计划的假设基础一直在变,做久了就是废纸。 

#### 转变 2:从文档优先到 Demo 优先 

团队基本不开传统站会了,改成"Demo 分享会"。有新想法就做一个能跑的原型,让内部用戶 试。有人用就继续打磨,没人理就算了"反正一个下午就能做出来,试错成本低。 两个操作技巧: 

- 写完需求文档,先别发给团队,先发给 Claude Code,看它能不能做出来。一个粗糙原型 比十⻚文档更能说明问题。 

- 做评估测试(evals),把模糊的"这个功能好不好"变成可测量的数据。 

#### 转变 3:每次新模型出来,把老功能重新过一遍 

上个月发布的功能,这个月新模型出来,可能突然变强了。Chrome 集成功能就是这么来的: 团队发现用戶已经在手动拼解决方案(在两个工具之间复制粘贴),那就直接做成产品功能。 操作方法:做重度用戶,故意为难 AI。让它做你觉得"应该做不到"的事。有时候它真的做到 了,那就是产品该跟进的信号。 反过来也一样:以前为了弥补模型不足写的复杂补丁,新模型出来后可能根本不需要了。 Opus 4.6 一次就删掉了 20% 的系统提示词"那些"拐杖"该扔就扔。 

#### 转变 4:保持简单实现,避免过度工程 

##### Anthropic 的信条:Do the simple thing that works。 

关键洞察不在"简洁好看",而在一个时间维度的理由:你费劲绕过的模型限制,下个月新模型 可能就消失了。你的"巧妙设计"反而变成累赘。实现越简单,以后升级越容易。 案例:Todo List 的自动提醒机制,老模型需要,新模型不需要,直接删了。类似情况反复出现 "系统提示词和工具说明越写越复杂,每次新模型出来都能扔掉一批。 

### 四、最难的转变:学会放手 

Cat Wu 的比喻:这就像冲浪。最重要不是控制浪,而是保持在浪头上。 

PM 的工作变成:找出少数几个绝对不能妥协的点,其他全部快速迭代。从"要不我们试 试......"到"来,试试这个",几乎没有时间差。 

### 五、关键数据 

AI 模型能力每 16 个月提升 41 倍(METR 数据)。 这意味着你今天的"做不到",两个月后可能就是标配。任何基于当前模型能力做的⻓期规划, 根基都在晃动。 

### 六、可操作的行动指南 

#### 对 Agent 开发 

- 不要追求"完美架构设计"。做一个能跑的原型,模型一变强就删掉补丁代码。 

- • 建立定期"扔拐杖"习惯:每次新模型发布,把现有的 skill/prompt 全重测一遍,删掉不再 需要的补偿性代码。 

- Ta 的信条应该成为你的第一原则:do the simple thing that works。 

- OPC 模式(AI 替代人工、快速试错)本身就是 side quest 文化的实践。 

- • 制度化:每周至少一个下午专⻔做 side quest,哪怕跟当前主线无关。 

#### 对技能管理 

- 定期审视:哪些 skill 是因为模型能力不够才写得很复杂?新模型出来了能不能精简? 

- • 质量 > 数量,但加一个定期评估的时间节点"每次新模型发布就是触发点。 

#### 对求职 

- 核心叙事不是"我会什么技术",而是 **"我能用 AI 把一个想法在下午变成能跑的东西"**。 

- • 这和 Cat Wu 的经历一模一样"她几百小时的工作量,一行代码没手写。 

#### 对团队协作 

- ⻆色边界正在模糊:设计师写代码、工程师做产品决策、PM 构建原型。 

- 这能运转的前提是清晰的战略和目标,让每个人都能自主优先级排序。 

- • PM 的核心工作变成三件事:在变化中创造清晰度、推动团队想更大的可能性、扫清挡路的 障碍。 

#### 对个人能力 

- Cat Wu 的职业线给了一个重要提示:跨行不是扔掉旧技能,是把同一套底层能力换应用场 景。找到你"跨场景可迁移的武器"。 

- 最被低估的 AI 技能:让模型反思自己的错误(ask the model to introspect on its own mistakes)。 

- Claude 的人格特质(低 ego、积极、高能力感)不是装饰品,是产品壁垒"提示系统设 计时值得参考。 

### 七、一句话总结 

- 别做⻓期计划,模型一变你的计划就是废纸。下午能试出来的事,别拖到两周后。做有效的简 单方案,模型变强了就扔掉拐杖。冲浪的时候,重要不是控制浪,是保持在浪头上。
